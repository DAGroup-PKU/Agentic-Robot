Code, not calls. A tool-calling robot agent spends a full LLM call, re-sending everything before it, on every one of the dozens of small steps a manipulation task takes; an agent that writes code can take many of those steps in one call.

This post introduces PyRUA-Lean, an open library built on a different idea: a robot becomes a Python object, and the agent acts by writing code against it. We compare it with a strong tool-calling agent on three simulation benchmarks, holding everything else fixed, and ask what the action format alone is worth: in success rate, in tokens and in dollars.

1. Why the action format matters

Robot manipulation is the worst case for one action per LLM call: many small steps, little reasoning per step, and a history that every step re-sends. The alternative is to let the model write its action as code. One LLM call can then run many primitives, loop over waypoints, branch on a sensor reading, and print only what the model needs to see next. This is the idea behind CodeAct (Wang et al., 2024), which found executable code actions more successful than JSON tool calls across 17 LLMs, and behind Code as Policies (Liang et al., 2023) in robotics. Software agents are moving the same way. Anthropic describes an agent that calls MCP tools from code and cuts one workflow from about 150,000 to 2,000 tokens (Anthropic, 2025). Cloudflare's Code Mode makes the same argument: with direct tool calls "the output of each tool call must feed into the LLM's neural network, just to be copied over to the inputs of the next call, wasting time, energy, and tokens" (Varda and Pai, 2025). OpenAI's computer-use guide offers a code-execution integration in which "one call can combine actions, loops, or conditional logic", and recommends it over structured mouse and keyboard actions for GPT-6 Astra (OpenAI, 2026a).

Robot agent frameworks mostly still act one tool call at a time. RPent, an open framework that steers frozen vision-language-action (VLA) models through memory-guided agents (Zhang et al., 2026), is a strong example: with memory, its agent reaches 92.6% across the eight LIBERO-PRO suites. That makes it the right baseline for a narrow question. If we hold everything fixed, including the model, the robot primitives, the perception and VLA services, the operating knowledge, the budget and the judge, and change only the action format, what happens to the success rate and to the cost?

2. How PyRUA-Lean works

PyRUA-Lean does for a robot what pyautogui does for a desktop: it turns the robot's primitives into plain Python calls that a program, or a model writing one, can script. Its design fits in four points.

  • A robot is a Python object. robo.move_to, robo.segment, robo.pi0_pick, robo.show and the rest map one to one onto the robot's primitives and return typed results. The API reference the model reads is generated from the same class, so the prompt cannot drift from the code.
  • One tool for any agent. The agent gets a single tool, python(code): a persistent namespace, a sandbox, and a ledger of every primitive call, with each episode's images, video and token usage recorded next to it. It runs under the Codex CLI and Claude Code.
  • The agent decides what to look at. A code cell returns what it prints. Camera images come back only when the code calls robo.show, instead of after every action.
  • Three robots, one contract. The Franka arm of LIBERO-PRO with π0.5, the two arms of RoboTwin 2.0 with LingBot-VLA, and the mobile manipulator of RoboCasa365 with RLDX-1, all running on RPent's robot stacks. A new robot is one class written against a short contract.

3. Research questions, and the short answers

RQ1Success rate. Does PyRUA-Lean reach the success rate (SR) of tool calling under the same budget?

AnswerYes, and higher on every benchmark. Its SR is higher by +11.0 points on LIBERO-PRO, +7.2 on RoboTwin 2.0, +7.8 on RoboCasa365's atomic tasks and +5.0 on its long composite tasks. Over the task instances of all four benchmarks together, PyRUA-Lean solves 12% more of them than tool calling: an SR of 71.0% against 63.1%.

RQ2Cost. How much cheaper is it?

AnswerMost where a task takes many steps that code can fold into one LLM call. On the tasks both agents solved, tool calling consumes 4.5× the tokens of PyRUA-Lean on LIBERO-PRO, 1.7× on RoboTwin 2.0, 1.5× on RoboCasa365's atomic tasks and 2.0× on its composite ones. Summed over the tasks both agents solved on all four benchmarks, PyRUA-Lean consumes 65% fewer tokens; LIBERO-PRO, whose episodes are the longest, weighs most in that total. At GPT-6 Astra's list prices the factors are 3.1×, 1.5×, 1.2× and 1.6×; a solved LIBERO-PRO episode costs $2.49 with tool calling and $0.79 with PyRUA-Lean.

RQ3Mechanism. Is the saving a property of the action format, or of the VLA policy and the guides that come with it?

AnswerThe format. Removing the VLA, the guides or both from both agents leaves tool calling the more expensive agent in every setting: 3.7–4.6× the tokens on LIBERO-PRO, 1.4–3.0× on RoboTwin 2.0 and 1.2–1.5× on RoboCasa365's atomic tasks. Without the VLA, PyRUA-Lean's SR lead grows to about 30 points.

RQ4Limits. When does PyRUA-Lean not pay off?

AnswerWhen one VLA call does most of the work. On RoboCasa365's atomic tasks the median PyRUA-Lean episode succeeds in its first LLM call. Its larger fixed prompt is then barely amortized, and at list prices the two agents cost about the same, $0.62 against $0.54 per solved episode.

4. Setup: change only the action format

Two ways to drive the same robot. The tool-calling agent is RPent's own. Each robot primitive, such as a move, a VLA grasp, segmentation, back-projection, a camera view or finish, is a tool, and the model calls one or more of them per LLM call. The PyRUA-Lean agent reaches the same primitives through robo behind the single tool python(code). PyRUA-Lean reuses RPent's robot stacks, services and primitive implementations, so both agents drive the same simulators, the same VLA and perception servers, and the same control code.

Held fixed. The planner model and its reasoning effort. The frozen models: the VLA policies, π0.5 on LIBERO-PRO (Physical Intelligence, 2025), LingBot-VLA on RoboTwin 2.0 (Wu et al., 2026) and RLDX-1 on RoboCasa365 (Kim et al., 2026), and SAM 3 for segmentation (Carion et al., 2025). The operating knowledge: both agents read the same zero-shot guides, and memory, recipes and audit steps are removed from both, because memory would turn the comparison into one about what was remembered rather than how the agent acts. The budget: 40 LLM calls and two hours per episode, or 100 calls for the composite tasks, which chain several atomic ones. And success, which is always the benchmark's own check, never the agent's claim.

Benchmarks and model. All 40 tasks of LIBERO-PRO's four perturbed suites (Zhou et al., 2025), all 50 RoboTwin 2.0 dual-arm tasks (Chen et al., 2025), and two sets from RoboCasa365 (Nasiriany et al., 2026): the 18 atomic tasks of Target50 and 32 composite tasks, each at five seeds. One task at one seed is a task instance, and each is run once with each agent. Both agents use GPT-6 Astra at high reasoning effort through the Codex CLI.

What we measure. SR, the success rate: the share of task instances that the benchmark's own check marks as solved. Token consumption: the prompt tokens an episode sends, summed over its LLM calls with cached tokens included; every call re-sends the conversation so far, so this is what the model reads. And the number of LLM calls. Cost is compared on the task instances both agents solved, as a ratio of totals: what each agent spent to solve the same tasks.

5. RQ1: a higher success rate

PyRUA-Lean reaches a higher SR on every benchmark: +11.0 points on LIBERO-PRO, +7.2 on RoboTwin 2.0 and +7.8 on RoboCasa365's atomic tasks. On the composite tasks, where neither agent solves half of the instances, the gap is +5.0 points. The failures differ in kind. Tool calling runs out of LLM calls one to four times as often: on 12.5% of the LIBERO-PRO instances, 15.6% of RoboTwin 2.0's and 11.1% of RoboCasa365's atomic ones, against 3.5%, 11.6% and 6.7% for PyRUA-Lean. Acting through code, the same number of calls goes further.

6. RQ2: fewer tokens, most on long tasks

Because every LLM call re-sends the history, PyRUA-Lean's saving should grow with the number of calls a task takes (Figure 3). Mostly it does. A solved LIBERO-PRO episode takes 21 LLM calls with tool calling and shows the largest gap; RoboCasa365's atomic tasks, where the VLA policy often finishes a task in one call, show the smallest. The composite tasks are the instructive exception: they take the most calls of all, 28, yet save less than LIBERO-PRO, because PyRUA-Lean halves the calls there without making them smaller.

On the LIBERO-PRO task instances both agents solved, a tool-calling episode made 21 LLM calls on average and a PyRUA-Lean episode 8. To reach success, the median tool-calling episode consumed 767k tokens and the median PyRUA-Lean episode 133k. PyRUA-Lean consumed fewer tokens on 100% of these instances.

Tokens are not the whole bill. GPT-6 Astra is priced at $10 per million input tokens, $1 for input read from the prompt cache, $12.50 for input written to it, and $50 for output, reasoning included (OpenAI, 2026b). Billing every LLM call of every episode at these prices, a solved LIBERO-PRO episode costs $2.49 with tool calling and $0.79 with PyRUA-Lean, 3.1× as much. On RoboTwin 2.0 the factor is 1.5× ($1.00 against $0.66), on RoboCasa365's composite tasks 1.6× ($2.01 against $1.25), and on its atomic tasks 1.2× ($0.62 against $0.54), close to parity. The factors are smaller than in tokens because caching discounts the re-sent history, and tool calling re-sends more of it. Output is at most 17% of either agent's bill on any benchmark, so how much each agent writes barely moves the factors. No LLM call in these runs went above 272K prompt tokens, where the price rises.

Failed episodes are left out of these ratios, because an episode that fails costs whatever its budget allows. Counting every episode gives 3.08× on LIBERO-PRO, 1.74× on RoboTwin 2.0 and 1.57× on the composite tasks, since failures are long for both agents. On RoboCasa365's atomic tasks the two bills become nearly equal, 1.11×: failures there run to about 40 LLM calls for both agents, and PyRUA-Lean's calls are the larger ones.

Where the saving comes from. Say an episode makes K LLM calls, and call k sends a prompt of Pk tokens. Its token consumption is the sum of these prompts,

T=∑k=1KPk=KP‾,
(1)

where P‾ is the average prompt of one call. Writing R for tool calling and C for PyRUA-Lean, a benchmark's token factor therefore splits exactly into two factors, the average number of LLM calls per episode and the average prompt per call, which Figure 5 plots against each other:

TRTC=KRKC⏟fewer LLM calls×P‾RP‾C⏟smaller calls

On LIBERO-PRO, 4.48× = 2.55× × 1.76×: PyRUA-Lean makes 2.55× fewer LLM calls per episode, and each call carries 1.76× fewer prompt tokens on average. The two factors are linked. Every call re-sends the conversation so far, so an episode with fewer calls also has less history to re-send, and its average call is smaller. Leaner results shrink it further: every tool result, three images included, stays in the tool-calling history, while a code cell adds only what it prints and the images it asks for. On RoboTwin 2.0 the two factors are 1.39× and 1.24×. On RoboCasa365's composite tasks fewer calls, 1.90×, carry nearly all of the saving. On its atomic tasks the episodes are short, so the first prompt dominates, and PyRUA-Lean's is the larger one (Section 8): its calls are the larger ones, a factor of 0.83×, and fewer calls, 1.84×, carry all of the saving.

7. RQ3: the format, not the VLA or the guides

Two confounds could produce this gap without the action format mattering. The VLA policy might suit code better, since one call can wrap a whole grasp. Or the shared guides might contain procedures that code can execute in bulk. So we removed each from both agents. No VLA deletes the benchmark's VLA policy from both agents' prompts, tool lists and code API, and refuses any call to it, which leaves perception and the scripted motion and gripper primitives. No guides gives neither agent the operating guides. Each ablation runs on a subset of a benchmark's tasks, named in Figure 6. On RoboCasa365 we removed only the VLA, on its atomic tasks; the composite tasks were not ablated.

Without the VLA, tasks take many more scripted steps, and PyRUA-Lean's SR lead widens: +30 points on RoboTwin 2.0 (an SR of 83% against 53%) and +20 on RoboCasa365's atomic tasks (66% against 46%). PyRUA-Lean makes up for the missing policy with code, a loop of approach, descend, close, lift and check, which the tool-calling agent has to issue one LLM call at a time. Without the guides the RoboTwin 2.0 gap shrinks to 1.4×, from 1.8× with them: in that setting PyRUA-Lean makes only a few fewer LLM calls than tool calling, 9 against 11 per solved episode.

8. RQ4: where the saving vanishes

The saving is smallest on RoboCasa365's atomic tasks, and at list prices it all but disappears. There the RLDX-1 policy does most of the work: the median solved episode reached success after 4 LLM calls with tool calling and 1 with PyRUA-Lean. With so few calls the first prompt dominates, and PyRUA-Lean's, which carries the full API reference, is the larger one: 24k against 17k tokens.

More LLM calls alone do not guarantee a larger saving either. Without the VLA, RoboCasa365's atomic tasks take 27 calls per solved tool-calling episode, more than LIBERO-PRO, yet the gap stays at 1.2×: PyRUA-Lean batches little there, making only 1.4× fewer calls, each of them larger. The composite tasks make the same point with the VLA in place: 28 calls per solved tool-calling episode, the most of any benchmark here, and a factor of 2.0×, because each PyRUA-Lean call there is about as large as a tool-calling one. So the claim is conditional. The saving scales with the number of steps that code can fold into one LLM call, and with how much each tool result carries; an agent that solves a task in one call has nothing to fold.

9. What this means for robot agents

  • Put a code tool in front of the primitives. PyRUA-Lean changes no primitive, VLA policy or guide; it only exposes them as a Python API behind one execution tool. That raised the SR and cut token consumption wherever a task takes more than a few LLM calls.
  • Return less to the model. Part of the saving is per call: a code cell returns what it prints and the images it asks for, while every tool result, images included, stays in the tool-calling history and is re-sent on every later LLM call.
  • Expect the saving to grow with the horizon, when code can fold the steps. Every extra LLM call re-sends a longer history, so long tasks gain the most when one code cell can take several of their steps. Tasks that one VLA call solves are the exception, and there a short tool list is cheaper than an API reference.

10. Build on PyRUA-Lean

PyRUA-Lean is open source, and we hope it grows into a shared convention for robot agents that write code: one way to hand a robot to a model, so that robots, primitives and agents from different groups fit together, and results from different papers can be compared. The repository holds the library, the batch scripts, the task-instance lists and the per-instance results behind every number in this post, so every figure here can be regenerated, every claim checked, and every change measured on the same task instances.

  • One convention for primitives. A primitive is a public method of the robot class, with a typed signature, a docstring and a typed result. The API reference the model reads is rendered from these, and every call is recorded in the episode's ledger. A primitive written this way works with every agent that drives python(code), and its documentation cannot drift from its code.
  • Add your own primitives, or choose the ones an agent may use. A new primitive is one more method, and it appears in the API reference by itself. A run already chooses its primitive set: the no-VLA setting of Section 7 hides the VLA primitives from the reference and refuses calls to them. We would like to extend this to named primitive sets, so that every experiment states exactly what its agent could call.
  • Improve the primitives that exist. Most of the primitives here are first versions: grasps can be more reliable, perception faster, and results shorter, which saves tokens on every later call, since each result stays in the history that later calls re-send. Because the batch scripts and task-instance lists ship with the library, an improvement can be measured on the same task instances, with the benchmarks' own checks, before it is merged.
  • More robots, runtimes and evaluations. A robot is one class written against a short contract, and any agent runtime that can call a tool can drive python(code); the three robots and two runtimes here are a start. Real hardware is the next step: there every action takes time, and fewer LLM calls should matter most. Longer-horizon tasks and memory are open too.

Issues and pull requests are welcome, from a clearer docstring to a new robot. The conventions above are how we will review them, and the benchmarks here are how we will check that a change helps.

11. Limitations and open questions

  • One planner model. Every number here comes from GPT-6 Astra.
  • Simulation only. A real robot adds latency to every action, which should favor fewer LLM calls, but we have not measured it.
  • Zero-shot only. Both agents start without memory. RPent's memory raises success substantially; whether code and memory compound or substitute for each other is open.
  • One tool-calling design. RPent is a strong framework, but tool calling can be engineered differently, for example with more tool calls per LLM call or compressed observations.
  • No wall-clock comparison. The latency of an LLM call on a shared model gateway varies too much from call to call to compare episode times fairly, so we compare tokens, LLM calls and dollars instead. PyRUA-Lean also executes as many simulator steps as tool calling or more, up to 1.3×, so on a real robot part of the time saved on LLM calls would be spent moving.
